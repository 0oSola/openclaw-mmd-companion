## 1. 本轮结果

桌宠已接入现有 V14D game 外观，正式 Electron 构建可加载真实克莱妲资源，保留默认参数并提供可收起微调。正常 pet 已启动，连接本机 8100；没有修改主站当前选择。入口仍为主站选择 V14D 游戏参考后，桌宠右键“同步主站”。

## 2. 原问题与影响

共享舞台原来仅使用构建时 API 地址，而桌宠配置在主进程运行时确定。模型、OCIO 等请求可能分流到不同端口。桌宠还缺少外观用户标识，微调栏会被更高层的窗口拖动接收面挡住。

## 3. 根因

消费端没有显式传入运行时地址及保存身份；共享组件的网页内定位不能跨越桌宠独立叠放层。桌宠普通模型目录与 V14D 白名单模型根目录也不是同一个约束。

## 4. 解决方式

App 等待 runtimeInfo 后读取共享配置，向 MMDStage 传入 assetApiBaseUrl、appearanceUserId 和 appearanceControlsPortal。V14D 模型目录读取已校验清单；非目标模型明确拒绝。微调面板放到文档根节点并排除拖动捕获，默认收起。加载错误提示不再被全高画布挤出窗口。

## 5. 修改前后行为

修改前可出现默认 8000 误请求、微调无法操作或参数不保存；修改后运行时地址用于整条相对资源链，曝光等参数按用户与模型保存到桌宠 localStorage。网页保存值不自动同步到桌宠，但两者截图默认值一致。材质、灯光、OCIO 公式、缓存和 SHA 校验未改。

## 8. 可复用知识候选

桌宠消费共享舞台时显式传递运行时资源地址，网页保留默认配置；从同一地址解析资源是客户端接入契约，不通过复制着色器解决入口差异。单元测试与正式 Electron 非默认端口资源观测支持该约束；未来 API 身份或地址策略改变时需重审。
